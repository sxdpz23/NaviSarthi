# NaviSarthi 0.8.0 — Console OTA updates

Status: **Planned**

Planned on 2026-11-11. No OTA implementation is retained in the app. The two
experimental Kotlin files and the standalone investigation/plan documents were
removed at the user's request; this milestone preserves the findings and future
requirements. OTA functionality stays out of versions before 0.8.0. No console
was connected or flashed, and no APK was built for this investigation.

## Goal and user flow

Update a qualified TFT console directly from NaviSarthi using official firmware.
Reimplement the original app's observable TFT behavior independently in Kotlin.
Scope excludes BLE Tripper and accessory updates, custom firmware and unattended
flashing. Do not bundle RE's proprietary implementation, firmware or embedded
credentials.

Provide **Settings → Console software update** with current firmware, update
availability, release notes, download progress, installation progress and verified
completion. An unavailable backend or unsupported console must show its actual
state rather than claim that the console is up to date.

1. Read console identity and partition versions.
2. Retrieve official metadata matching the exact console, vehicle variant, region
   and applicable base version. Establish legitimate authenticated access before
   enabling discovery; do not copy the original app's credentials.
3. Download and validate the official ZIP, checksum, manifest and partition binaries.
   Bind validation to the same package bytes subsequently used for transfer.
4. Require an explicit **Install** action, a parked motorcycle and verified
   power/readiness conditions. Resolve the source and meaning of power signals on
   hardware before defining installation thresholds.
5. Pause navigation/media transfers and give the updater exclusive ownership of
   the console session. Keep installation alive through normal backgrounding.
6. Transfer partition headers and data using negotiated block sizes, matching
   acknowledgements and bounded retries. Report pending, rejected and timed-out
   replies separately; never advance from an unacknowledged block.
7. Verify every required partition, reconnect after reboot, and reread installed
   versions before reporting completion. A local UDP send or 100% bytes sent is
   insufficient evidence of success.

Allow download cancellation. During installation, expose interruption/recovery
actions only when the console protocol has been verified to support them. App
restart or lost connectivity must not automatically restart a flash.

## Diagnosis from the original APK

These are static observations from the supplied local APK, not proof of current
backend availability, exact reply layouts or supported hardware.

- Reference: `builds and versions/OGRE.apk`; SHA-256
  `d08478e8c564624503b440834a40499cd4acdc1c8572e49fe1b4830472ad37a4`.
  Relevant classes were inspected from `classes.dex` and `classes8.dex`. Local
  decompilation artifacts remain under ignored `.gradle/ogre-analysis`; they must
  not be committed or packaged.
- TFT update flow: `InfotainmentActivity`, `SoftwareUpdateActivity`, `vk6`
  (transfer logic), `wcb` (manifest), `y91` (binary slicing), `ph7` (block framing),
  `y2c`/`sw2` (Wi-Fi metadata transport). Separate BLE updaters in the APK must not
  be mistaken for this TFT path.
- Local identity mappings include RAC00398 → K1G, RAC00975 → K1F and RAM00309 →
  P3K. These do not independently establish motorcycle compatibility.
- The APK POSTs `firmwareDeviceType`, `region` and `vehicleVariant` to
  `otap/otap/firmwaredownload`. Its production base string is
  `https://api-tbt.royalenfield.com/v3/`. The response supplies firmware version,
  campaign name, firmware URL, checksum and optionally release notes. Its HTTP
  interceptor supplies an Authorization header. NaviSarthi access is unresolved;
  no backend request or credential reuse was performed.
- The stock downloader checks `bin.zip` with SHA-256 before extraction. A checksum
  establishes integrity relative to trusted metadata, not vendor authenticity by
  itself. Independent Android-side signature verification was not identified in
  the inspected flow; console-side verification remains unknown.
- Software information uses request TLV `0A/02`, value `AA55000000000000`, and
  reply `0B/02`. Stock code reads ten eight-byte partition/version records; record
  1 supplies the displayed application major/minor version. Validate framing,
  ordering, record contents, failure markers and permitted lengths against real
  replies before implementing a strict parser.
- `reflash_manifest.xml` contains Application/Calibration entries with FileName,
  HeaderFileSize and VisteonSWPartNumber. Stock parsing expects at least ten
  unique partitions; final verification explicitly handles IDs 0–9. Binary
  slicing assumes a 256-byte header. Confirm this layout with an official package.
- Transfer sequence: reflash request `0A/01`, block negotiation `0A/03`, partition
  setup `0A/06`, header/data blocks `0A/04`, partition checks `0A/05`, final
  verification `0A/07`. Replies use `0B` with the matching subcommand. Blocks use
  a big-endian index. Stock positive status is `AA`; `55` carries negative/pending
  status, with `78` indicating pending. Static logic shows a five-second timer and
  a five-retry counter; qualify actual retry and terminal-failure behavior.
- Stock final verification checks ten positive partition statuses, then shows a
  reconnect flow. Its pre-install battery check compares a value to 50; the power
  source and meaning have not been established. Do not assume it measures the
  motorcycle battery or transplant questionable version comparison, signed-byte
  arithmetic or permissive manifest parsing.

## Implementation structure

- Separate official metadata discovery, package download/validation and console
  transfer behind dedicated interfaces. Metadata and validated-package results
  must retain target identity, version constraints, checksum and package reference.
- Use a lifecycle-aware controller exposing observable states: unavailable,
  checking, up to date, update available, downloading, validating, ready to install,
  installing, verifying, reconnecting, completed, failed and recovery required.
  Keep download progress distinct from installation/verification progress.
- Run installation in a foreground service appropriate to Android 14+ connected
  device work. Own required session/resources for the update lifetime and prevent
  concurrent navigation/media writers. Restore ordinary operation only after the
  console is confirmed ready or the update session is safely released.
- Persist target/package identity, update phase, last acknowledged transfer
  position and failure reason for diagnosis and verified recovery. Do not persist
  credentials in diagnostics or interpret saved progress as permission to resume.
- Validate archives with bounded compressed/expanded sizes, safe paths, duplicate
  detection and XML external entities disabled. Reject unsupported layouts,
  missing binaries, mismatched part IDs and unverified target/base versions.
- Ship installation disabled for unqualified console/firmware combinations. Keep
  current app version/build configuration unchanged during this planning work.

## Verification and release gates

1. Resolve legitimate metadata/package access. Obtain an official ZIP with trusted
   metadata for the exact console, a read-only console identity/version capture,
   and a stock-app update trace covering acknowledgements, verification, reboot
   and reconnection. Validate recovery behavior before installation trials.
2. Unit-test malformed packages, wrong checksums, incompatible targets/base
   versions, duplicate/missing partition IDs, unsupported headers, unsafe ZIP
   paths, oversized expansion and XML entity attacks.
3. Test full datagram framing, truncated/negative/pending replies, negotiated block
   boundaries, index limits, duplicate/out-of-order acknowledgements, lost replies,
   retry exhaustion and final partition verification with recorded fixtures and a
   simulated console. Synthetic success alone does not qualify hardware.
4. Test navigation/media suspension and restoration, backgrounding, phone screen
   lock, connection loss, process/service restart, console reboot and post-update
   version checks. Ensure saved sessions never trigger automatic flashing.
5. Perform controlled parked-bike trials with verified power and an established
   recovery procedure. Qualify every supported console/firmware combination
   separately before enabling it in v0.8.0.
6. Run Android compilation and relevant regression tests when implementation
   begins. Record package provenance, qualified combinations, test results and
   outstanding limitations here before release. Logs must omit credentials and
   unnecessary personal identifiers.

## Outstanding evidence and current verification

The user confirmed that neither an official firmware ZIP nor an update capture
is available. Legitimate metadata access, a real console version reply, package
compatibility, power checks, recovery and post-update behavior are unresolved.
Installation remains gated until these dependencies are resolved.

This change is cleanup and planning only. Verify removal of the four experimental
files, absence of application references to them, roadmap linkage, and preservation
of unrelated work. No runtime implementation, hardware acceptance or build/test
success is claimed for v0.8.0.
